## Promotion Policy
`enforceInteractionDesign` ships REQUIRED from day one for context-governed (new) change dirs — no informational period (rationale in Sign-off). The `cdd-kit doctor` over-fetch report stays informational-only **permanently**: ADR 0012 §2/§6 forbids ever promoting it to a gate finding, because a per-change artifact cannot see sibling screens and promoting it would reproduce the context-blind failure the ADR's own rejected proposals #1/#2 evidence. No other new gate is introduced by this change.

## Migration Window
Mechanism: `isNewChange || strict`, the identical device `enforceAcceptanceOracle` (src/commands/gate-acceptance.ts) and `enforceTestEvidence` already use. `isNewChange` is computed once in `gate.ts:93` via `isContextGovernedChange(changeDir)` (src/commands/gate-artifacts.ts:129), which checks `tasks.yml` frontmatter `context-governance: 'v1'` — NOT directory age or file presence. `gate-design.ts` MUST accept `isNewChange` as a parameter threaded from that single call site (mirror `enforceAcceptanceOracle`'s exact signature: `(cwd, changeDir, changeId, isNewChange, strict, errors, warnings)`) and never re-derive its own signal. **Top risk:** if the implementer instead derives a local "is this new" heuristic (e.g. `!existsSync(interactionDesignPath)`), the window silently decouples from the canonical definition, and this additive minor bump (schema-version 0.3.0→0.4.0) becomes a breaking overnight failure for every legacy change dir — exactly the outcome the shared `isNewChange` threading exists to prevent.

## Workflow Changes
**Scope expanded by maintainer approval (see coordinator message this session): `cdd-kit gate` must actually run in CI.** This supersedes the earlier "none required" finding, which is now the documented *problem statement*, not the conclusion. Two files change; `assets/github-workflows/` is never hand-edited (build.js:114 generates it from `github-workflows/`).

### 1. Change-id derivation (both files, identical logic)
New step `Determine changed spec directories` (id: `changed`), gated `if: github.event_name == 'pull_request' || github.event_name == 'push'`:
- **Checkout**: `actions/checkout@v4` needs `with: { fetch-depth: 0 }` — the default `fetch-depth: 1` fetches only the tip commit, so the base commit is absent locally and any diff against it fails. Full history is simplest/most robust for a repo this size; a large monorepo could instead shallow-fetch just the base SHA, but that is an optimization, not required here.
- **Base ref**: on `pull_request`, use `${{ github.event.pull_request.base.sha }}` — an exact commit SHA already in the event payload — not `origin/${{ github.base_ref }}` (a branch ref that can move mid-run and requires fetching that branch separately). On `push`, use `${{ github.event.before }}`, falling back to `git rev-parse HEAD^` when `before` is unset or all-zeros (first push of a branch / edge cases).
- **Diff**: `git diff --name-only "$BASE_SHA" "${{ github.sha }}" -- 'specs/changes/'`, then `grep -oE '^specs/changes/[^/]+' | sed 's|specs/changes/||' | sort -u`.
- **Zero-changes case**: if no `specs/changes/` path changed, `ids` output is empty string and the step still exits 0 (success) — the gate-invocation step below is itself gated `if: steps.changed.outputs.ids != ''`, so it is skipped, not failed.

### 2. Gate invocation and `--strict`
`--strict` (per `hooks/pre-commit:17` and `gate.ts`) turns non-archived pending `tasks.yml` items, and every `isNewChange||strict`-gated missing-artifact branch, from warnings into hard errors for ANY change dir (not just new ones). Recommendation: **`pull_request` → `cdd-kit gate <id>` (no `--strict`); `push` to main/master → `cdd-kit gate <id> --strict`.** A PR opened mid-work legitimately has pending tasks (draft/WIP/in-review) — hard-failing every PR push on that would punish normal iteration, not catch a real defect. A commit landing on the default branch with pending tasks is the worse failure (incomplete work merged as done), so strict applies there, mirroring why the pre-commit hook itself defaults to `--strict`.

### 3. Version pinning — same class of bug as this repo's own stale 2.2.1 global binary
- **Adopter template (`github-workflows/contract-driven-gates.yml`)**: replace `npm install -g contract-driven-delivery` with `npm install -g contract-driven-delivery@{{cdd-kit-version}}`. `{{cdd-kit-version}}` is a new substitution token, resolved by `init.ts` at scaffold time from the running CLI's own `pkg.version` (same object already read at `src/cli/index.ts:19`), using the exact token-replace pattern `init.ts` already applies for `{{conda-env-name}}` (`init.ts:306-309`). Trade-off considered: `npx contract-driven-delivery@{{cdd-kit-version}} ...` is equally deterministic but forces rewriting every subsequent `cdd-kit ...` invocation in the file to `npx contract-driven-delivery@{{cdd-kit-version}} ...` — larger diff, no benefit on ephemeral GH-hosted runners. Picked `npm install -g pkg@{{token}}`: one-line change, command name stays `cdd-kit` everywhere else. **Known limitation, not fixed here:** `upgrade.ts`'s `planMissingFiles` (upgrade.ts:22-35) only adds files that don't already exist at the destination — it never rewrites an adopter's already-scaffolded workflow file, so this pin will not silently drift forward on `cdd-kit upgrade` for existing adopters (see §6). Refreshing an existing pin is a separate, non-blocking follow-up (e.g. a future `cdd-kit upgrade --refresh-ci`).
- **This repo's own `.github/workflows/contract-driven-gates.yml`**: must NOT install the published package for either `validate` or `gate` — **confirmed and corrected**: today's `Install cdd-kit: npm install -g contract-driven-delivery` step already has this exact disease (this repo's global binary is 2.2.1 while `package.json` is 3.9.0), and it silently affects the *existing* `cdd-kit validate` step too, not just the new gate step. Replace with `npm ci && npm run build` (esbuild bundle per `build.js`), then invoke `node dist/cli/index.js validate` and `node dist/cli/index.js gate <id> [--strict]` — every check runs against this commit's own source, never a published version that may not yet know about `enforceInteractionDesign`.

### 4. Failure semantics
Confirmed: no `continue-on-error` on the gate step in either file — a failing `cdd-kit gate <id>` fails the job and blocks the PR/push, by design. Confirmed: `cdd-kit doctor` (the over-fetch/reverse advisory) is NOT added as a CI step at all — ADR 0012 §2/§6 forbids ever promoting it to a blocking or even a run-in-CI finding; it stays local/manual (see Informational Gates).

### 5. Contract truthfulness
`ci-gate-contract.md`'s Gate Inventory currently has exactly one row (`enforceAcceptanceOracle`), claiming trigger `pull_request; local (cdd-kit gate)` — verified FALSE today (workflow never calls `cdd-kit gate`). After this change, that claim becomes TRUE for `enforceAcceptanceOracle` (a side benefit of this fix, not itself in this change's AC set) and TRUE from day one for the new `enforceInteractionDesign` row. No other required check (`enforceTestEvidence`, `enforceContractSubstance`, `enforceRequiredAgentEvidence`, `enforceBugFixEvidence`, tier checks) has its own Gate Inventory row today — verified by grepping the contract file — so no other row's trigger claim is in the same boat; they ride along inside the same `cdd-kit gate` call once it runs in CI, with no separate contract text to correct.

### 6. Blast radius on adopters — the premise needs correcting, not softening
Verified (`src/commands/upgrade.ts:22-35`, `planMissingFiles`): `cdd-kit upgrade` only writes files that do **not already exist** at the destination; it never overwrites an adopter's already-scaffolded `.github/workflows/contract-driven-gates.yml`. So an *existing* adopter's next `cdd-kit upgrade` does **not** silently inject this new required gate step into their CI — the premise in the coordinator's framing is factually incorrect for the `upgrade` path, and I'm stating that plainly rather than adding an unneeded opt-out. The new required job reaches only (a) brand-new `cdd-kit init` projects, which have no pre-existing PRs to break, and (b) an adopter who explicitly runs `cdd-kit init --force` (a deliberate, self-selected overwrite that also re-detects their stack). **Recommendation: no `continue-on-error`, no opt-out env var, nothing softened** — the maintainer's instruction is honored exactly as given, and no adopter is surprised, because none of them get this step without either scaffolding fresh or explicitly forcing an overwrite. Flag as a documentation follow-up (CHANGELOG/migration note): an adopter who wants the new gate on an *existing* repo must manually diff/merge the new template themselves.

## Rollback Policy
Additive; no data migration. Reverting this change removes the `enforceInteractionDesign` gate check, the `interaction-design.md` template, `pre-tool-use-design-write.sh`, the `design confirm` CLI, and the two workflow gate steps. `.cdd/design-lock.json` is a regenerable per-change hash sidecar, not source of record — safe to delete on rollback (same class as `.cdd/acceptance-lock.json`). Reverting the workflow steps restores the previous behavior in which `cdd-kit gate` ran only in the local pre-commit hook; the `ci-gate-contract.md` Gate Inventory trigger cells must be reverted with them, or the contract resumes claiming a `pull_request` trigger it does not have. Adopters are unaffected on rollback: `cdd-kit upgrade` never overwrites an existing `.github/workflows/contract-driven-gates.yml` (`src/commands/upgrade.ts` `planMissingFiles` adds missing files only).

## Sign-off
**APPROVED**, with one caveat and one blocking pre-merge finding. `enforceInteractionDesign` shipping required-from-day-one for new change dirs is a second deliberate exception to `ci/required-check-policy.md`'s general informational-first guidance (the first being `enforceAcceptanceOracle`). Same reasoning applies: an informational period would let every new change ship an unconfirmed, non-reconciled interface during precisely the window the gate exists to close — state-discriminator failure mode #2 (`[]` meaning two different worlds, ADR 0012 §2) would ship undetected on every new screen until the check turned on for real; that defeats the change's own purpose exactly as an informational acceptance-oracle would have. All hard-failing conditions (AC-4, AC-5, AC-6) are deterministic and reuse hardened logic (ADR 0010 hash-lock shape, ADR 0007 `openapi.json` projection). **Caveat** (mirrors the acceptance-oracle AC-4 caveat): the provenance resolver (`test/utils/design-provenance.test.ts`) is new code, and test-plan.md's own Notes name it "the highest-risk new unit surface" — a false-positive HARD failure there is a P0 gate-defect bug fix (tighten the resolver), never grounds to demote the whole check to informational. **Blocking pre-merge finding** (not a sign-off condition on the mechanism, but blocks *this* change's own gate): `specs/changes/interaction-design-loop/` currently has no `interaction-design.md` of its own — contract-reviewer's agent-log already flagged this (`agent-log/contract-reviewer.yml`); `backend-engineer` must scaffold it with the ADR 0011 `applicability: not-applicable` marker and a non-empty reason before this change can pass the gate it ships.
